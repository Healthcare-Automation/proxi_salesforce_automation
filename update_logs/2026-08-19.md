## Parser: handle office number with no dash ("4412 Humble, TX") + job 20311 repair

- **When:** 2026-08-19
- **Area:** `src/utils/job_content_parser.py` (`_parse_city_state`), `tests/test_job_content_parser.py`, one-off repair script (scratchpad)
- **What:**
  - Kimedics labeled a new practice `4412 Humble, TX` — office number with **no dash**. The dash-requiring prefix regex didn't strip it, so the comma split produced `city='4412 Humble'`. Result: a duplicate worksite Account "Aspen Dental - 4412 Humble, TX" (001UP00000kMVieYAG) alongside the same-day "Aspen Dental - Humble, TX" (001UP00000kLCenYAG), with Job__c a01UP00000kMRbpYAG attached to the misnamed one and `Job_City__c='4412 Humble'`.
  - Fix: when a practice value starts with a 3–5 digit number followed by whitespace (no dash) and the remainder still looks like a location (contains a comma, or ends in a validated 2-letter state code), strip the number and treat it as the office prefix. Covers `4412 Humble, TX`, `4412 Humble TX`, `1029 Keizer. OR`. Guarded so bare `4412 Humble` (no state signal) stays unparsed. Tests: 61/61 parser, 318 suite.
  - Repair executed against SF + Supabase: job repointed to 001UP00000kLCenYAG, `Job_City__c` fixed to `Humble`, duplicate Account deleted (verified 0 references first), `job_current` + `sf_worksite_location_map` mirrored. All steps read back clean.

## Email-as-status-truth: Kimedics emails now drive job status

- **When:** 2026-08-19
- **Area:** `src/utils/email_status_signal.py` (new), `src/utils/gmail.py`, `src/utils/pipeline_link_scrape.py`, tests (`test_email_status_signal.py`, `test_email_status_pipeline.py`, gmail parser test)
- **What:**
  - `gmail.py`: status-update emails were truncated to one word (`status: Active` — ambiguous). Regex now captures the full label ("Active, not accepting new providers"). Historical truncated rows are deliberately ignored by the new logic.
  - New `email_status_signal.resolve_status_with_email`: explicit `status: X` emails set the status — a FRESH one (≤30 min, first processing) overrides a contradicting page; a stale one (auto-retry of an old email) never beats the live page but logs a mismatch. First-notify ("new") emails imply "Active, accepting new providers" but only FILL a missing/unrecognized page status. No email status is applied unless it's the newest status-bearing email for the job (prevents stale retries rolling status back — same failure class as the overwrite bug).
  - Wired into `process_link_scrape_batch` Pass 1 BEFORE validation, so the validator and everything downstream (open-date history, create-then-flip-Open, SF push) see the effective status. New events: `status_filled_from_email` (silent recovery), `status_email_page_mismatch` (added to the per-batch alert signal set — mismatches email the operators).
  - **Impact analysis done first:** open-date logic keys statuses by email date → email-derived statuses slot in correctly; validator sees only known labels; roster-only detection unaffected; daily-summary metrics count unaffected event types; dashboard shows new events as generic timeline cards.
- **Net:** a 20311-style incident now creates the job as Open from the first-notify email even if the page's status field is unreadable, and any page/email disagreement alerts within minutes instead of surfacing as a client complaint the next morning. Suite 333 green. Deployed to Modal same day.
